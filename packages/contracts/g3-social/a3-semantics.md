# A3 presentation state — draft 3

`schema.json` and generated TS/Rust/protobuf/descriptor/golden fixtures are the shared wire contract. Existing HUD, POI, chat and transient event-ID derivation are unchanged. Emote IDs are the 20 legacy catalogue IDs; robes are red/orange/yellow/green/blue/purple. `hat`, `amulet`, `gem` are validated client reports of secret_hat/secret_amulet/secret_amulet_gem, never achievement grants.

Publish remains `{eventId, sequence, emote:{emoteId,active}}` or `{eventId, sequence, cosmetic:{robeId,hat,amulet,gem}}`. A deliberate repeat uses a new higher sequence and corresponding deterministic original event ID. Retrying an original uses exactly its original identity/payload; duplicates neither restart nor renew state. An older unknown sequence conflicts; original retry answers remain bounded to 64 per session/kind. A stop uses `active:false` with a valid catalogue ID and a new higher sequence. It stops the current emote regardless of that ID. A true-to-false cleanup is allowed even when the four-starts-per-second selection budget is exhausted; redundant new stops remain budgeted. Cosmetic originals remain two per second. Route/read/room gates are unchanged.

Snapshot emote/cosmetic projections have positive `presentationRevision` (field15), original `eventId`/`sequence`, and no `expiresAt`. Revision orders the current state per run/world/kind, including cosmetic owner-session turnover. HUD continues using `hudStateRevision` only. Snapshot identity/scope always names the current eligible owner; the original event ID/sequence identifies the accepted action and is not recomputed from rewritten snapshot scope. Cosmetic recovery is restoration, not a newly accepted colour-change action; cold snapshots must not spawn colour-change particles.

`EmoteState.ageMs` (field4) is server elapsed time since original acceptance, saturated to uint32. It is regenerated on reads; a duplicate does not reset it. `durationFrames` is exactly the legacy catalogue value (0 loops). At 60 game frames/second, a finite emote is complete at `floor(ageMs*60/1000) >= durationFrames+2`, matching the legacy `frames_emoting-1 > frames` boundary. A completed snapshot returns `active:false` with the same original/revision; it must never start animation/particles. A receiver accounts conservatively for request transit using its local monotonic clock, never cross-machine wall-clock agreement; repeated snapshots of the same original update age without restarting. Explicit stops/replacements have a new revision. Looping state has no presentation TTL. These rules do not grant indefinite delivery permission: current canonical roster/capabilities still gate every read.

One current row per run/world/kind is retained. Emotes are bound to the publishing game session and are stopped on lost playing eligibility/death/owner replacement/service restart; they never resume across Continue. Cosmetics may restore for the same durable world/principal after revalidation, with the current owner/session/scope, while nonterminal actor identity exists. Disconnected/removed actors are omitted from snapshots; terminal/removal cleanup deletes their state. Current eligible recipients are selected on each read, so a new peer/cold owner can obtain current cosmetics and a still-active peer emote. Client protection/form replacement/menu-disable must cancel local owned effects and send/coalesce a newer stop when permitted. A lost stop reply retries the original or reconciles its current/newer snapshot; never issue periodic new starts to maintain a loop.

Canonical examples are in `fixture-inputs.json` and `golden.json`: >30s loop, partly elapsed timed effect, completed timed effect, explicit stop, retained cosmetics. Engine animation, sound, control ownership and M-Nee behavior still require Client adapters and later actual Noita checks.
